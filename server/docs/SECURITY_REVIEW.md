# セキュリティレビュー報告

対象:`server/` 配下の全コード(サーバー・画面・スクリプト)。
方法:コードの通読、攻撃を想定した入力での実動作確認(壊れた入力・権限越え・改ざん・使い回し)、自動テスト(19件)。

## 1. レビュー中に見つけて、修正済みのもの

| # | 重要度 | 内容 | 対処 |
|---|---|---|---|
| F1 | **高** | 壊れたCookie(例:`%E0%A4%A`)を1回送るだけで、そのリクエストが応答せず固まる(サーバーに悪意ある入力で負荷をかけられる) | Cookieの解読を安全化。全リクエストに「最後の保険」の例外処理を追加し、必ず応答を返すようにした。回帰テストあり |
| F2 | 中 | リクエスト本文が `null` や配列だと、500エラーになる(想定外の入力で処理が失敗する) | JSONのオブジェクト以外は400で拒否 |
| F3 | 低 | 壊れたURL(`/%E0%A4%A`)で500エラー | 400で拒否 |
| F4 | 低 | ログインのロック発生・管理者ログインが記録に残らなかった | 修正履歴(監査ログ)に記録するようにした |

## 2. 要件ごとの確認結果

| 要件 | 結果 |
|---|---|
| パスワードはハッシュ化 | ✅ scrypt(ソルト付き)。平文はDB・ログ・バックアップのどこにもない。テストで確認 |
| 権限チェックはサーバー側 | ✅ 全APIの入口(`authHook`)で、ログイン・管理者権限・初回パスワード変更済みかを確認。社員が管理APIを呼ぶと403、他人の申請は404。テストで確認 |
| 秘密鍵は `.env` | ✅ コードに秘密値なし。`.env` はGit管理対象外。起動時に未設定・短すぎる場合は起動を拒否 |
| XSS対策 | ✅ 画面は文字列からHTMLを組み立てず、`textContent` で表示。さらにCSP(`script-src 'self'`、インラインスクリプト禁止)、`X-Content-Type-Options: nosniff` |
| Excel数式対策 | ✅ 全セルを文字列セルで出力し、さらに `= + - @` で始まる文字には `'` を前置。出力ファイルに数式セル(`<f>`)がないことをテストで確認 |
| ログイン失敗でロック | ✅ 社員コード単位(5回→15分)とIP単位(20回→15分)。存在しないコードでも同じ応答・同じ処理時間で、社員コードの存在を推測されにくい |
| 打刻の不正対策 | ✅ トークンはHMAC署名+発行時刻+タブレットID。有効60秒。使用済みトークンはDBに記録し、同時アクセスでも1回しか成功しない。改ざん・期限切れ・解除済みタブレットのQRは拒否。時刻は常にサーバー時刻 |
| タブレットの限定 | ✅ 登録コード(15分・1回限り)で端末にランダムな鍵を持たせる。DBにはその鍵のハッシュだけを保存。未登録・偽造Cookieは403 |
| 修正履歴 | ✅ 元の打刻は削除不可(DBのトリガーで拒否)。履歴テーブルは追記専用(更新・削除をDBが拒否)。理由は必須 |
| CSRF | ✅ 変更系は「独自ヘッダ+同一オリジン」必須。Cookieは `HttpOnly; SameSite=Lax`(タブレットは `Strict`) |
| SQLインジェクション | ✅ すべてプレースホルダ。文字列連結のSQLは、数値に丸めたLIMITのみ |
| ファイル公開範囲 | ✅ `public/` 以外(`.env`・DB・ソース)は取得できない。`..`、`%2e%2e`、NULL文字、壊れたエンコーディングも拒否。テストで確認 |
| 外部通信なし | ✅ CDN・外部APIなし。QR生成ライブラリは `vendor/` に同梱(MIT)。CSPでも外部への接続を禁止 |

## 3. 残っているリスク(運用で対処・了承が必要なもの)

| # | 重要度 | 内容 | 対処・推奨 |
|---|---|---|---|
| R1 | **中** | **通信が暗号化されていない(HTTP)**。社内Wi-Fiに悪意ある人がつながると、ログイン時のパスワードや、ログイン中のCookieを盗み見される可能性がある | Wi-FiをWPA2/WPA3+強いパスワードにし、パスワードを知らない人(来客)をつなげない(ゲストWi-Fiを分ける)。将来HTTPS化する場合は `.env` の `COOKIE_SECURE=true` を使う(各スマホに証明書を入れる作業が必要) |
| R2 | 中 | **QRの写真を使った代理打刻**。社内Wi-Fiにつながっている人が、タブレットのQRを撮影して、60秒以内に別の場所にいる同僚に送ると、その同僚が(同じWi-Fi内なら)打刻できる。社外からは、サーバーに届かないので不可 | 完全には防げません。タブレットを、人目のある入口に置く。「日別」画面で、打刻の状況を定期的に確認する。有効時間を短くしたい場合は `QR_ROTATE_SECONDS` / `QR_TTL_SECONDS` を小さくする(例:15 / 30。ただし読み取りの猶予も短くなる) |
| R3 | 中 | **パスワードの貸し借り**。他人のコードとパスワードで打刻される | 社内ルールで禁止。「修正履歴」で、打刻の不審な点を確認する |
| R4 | 低 | **ロックの悪用**。他人の社員コードで5回わざと間違えると、その人が15分ログインできなくなる | 管理者の「パスワード再設定」でロックを解除。ロックの発生は修正履歴に残る |
| R5 | 低 | **バックアップにパスワードのハッシュと個人情報が含まれる** | バックアップ先のフォルダ・外付けディスクを、他人が見られないように管理。可能なら、サーバーPCと外付けHDDをBitLocker(Windowsの暗号化)で保護 |
| R6 | 低 | **サーバーPCに物理的に近づける人は、`.env` やデータファイルを読める** | サーバーPCを施錠できる場所に置き、Windowsのログインパスワードを設定。`C:\kintai` を、管理者以外が読めないよう権限を設定 |
| R7 | 低 | 管理者のログイン状態は7日間続く(社員は60日) | 共用PCでは、管理画面の「ログアウト」を押す |
| R8 | 低 | **サーバーPCの時計**。インターネットがないと時刻が少しずつずれ、打刻時刻もずれる | 月に1回、Windowsで時刻の同期を行う。タブレットの時計表示はサーバーの時刻なので、ずれに気づけます |
| R9 | 情報 | Node.js標準のSQLiteは「実験的機能」と表示される(ログに警告が出る)。動作は安定しているが、将来のNode.js更新で仕様が変わる可能性 | Node.jsのバージョンを勝手に上げない。更新する場合は、先にバックアップを取り、`npm test` を実行 |
| R10 | 情報 | 打刻関連以外のAPIに、回数制限はない(ログインのみロックあり) | 社内LAN限定・10名規模のため許容 |

## 4. 確認していないこと

- **Windows 11 上での、自動起動・ファイアウォール設定・`.bat` の動作確認はできていません**(開発環境がLinuxのため)。設置時に、手順どおり実機で確認してください(マニュアル 2章・5章)。
- 実際のスマホ(iPhone / Android)の標準カメラでの読み取りは未確認です(QRの生成とURLの内容、ブラウザでの表示は確認済み)。
- 外部の専門家による侵入テストは行っていません。

## 5. 自動テストの範囲(`npm test`)
- 既存HTMLの計算ロジックと、移植した計算が一致すること(4,320パターン+締め期間800日)
- 権限(未ログイン/社員/管理者)、CSRF、ログインロック
- QR打刻(出勤前の退勤・再出勤の警告、二重打刻、トークン使い回し、期限切れ、改ざん、解除済みタブレット、サーバー時刻の強制)
- 残業申請の承認フロー、自己承認の禁止、承認後の本人修正禁止
- 打刻と申請の食い違い警告(1分差でも警告)
- 修正履歴の追記専用、元の打刻の削除禁止
- 社員マスタ(重複、初回パスワード変更必須、無効化)
- Excel出力(シート・打刻列・数式無害化)、バックアップ・世代管理、旧データ取り込み
- 壊れた入力への耐性
